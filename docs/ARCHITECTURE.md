# Architecture

This file covers the modules and the request flow that exist now. The target
design (all five modules and the full request pipeline) is in the plan's
[Architectural decisions](../plans/weather-chatbot.md#architectural-decisions).

`security.py` imports only `config.py` from the app's own modules. `weather.py` imports `security.py` (for `REQUEST_TIMEOUT_SECONDS` and `log_error()`), and so does `agent.py` (for `CANARY` and `log_block()`), so `security.py` can import neither back: `app.py` trims the history with `trim_history()` and hands it to the classifier.

[.streamlit/config.toml](../.streamlit/config.toml) sets `client.showErrorDetails = "none"`, so an unexpected exception never shows its details in the browser.

## Request flow

Streamlit runs `app.py` from the top on every interaction:

1. `check_keys(load_env())` runs first. Both `XAI_API_KEY` and `OPENWEATHER_API_KEY` are required. If either fails, the page shows `setup_message()` with `st.error` and calls `st.stop()`, before any model is created.
2. `get_model()` wraps `create_model()` in `@st.cache_resource`, so one `ChatXAI(model="grok-4.7", max_tokens=500, timeout=10)` is reused across reruns. `get_classifier_model()` does the same for `create_classifier_model()`, a second `ChatXAI(model="grok-4.7", temperature=0, max_tokens=200, timeout=10)`. Each is created the first time a message gets that far, not at startup.
3. `units_toggle()` draws the sidebar `st.segmented_control` (°F or °C, `required=True` so it can't be cleared, session-state key `UNITS_KEY`) and returns `"imperial"` (the default) or `"metric"`. This is the only place units are chosen.
4. Chat history lives in `st.session_state.messages`. Each entry is `{"role", "content"}`, and assistant entries also carry `"cards"`, the raw tool results to draw. A message the free gate or the classifier blocked, and its refusal, also carry `"blocked": True`. When a question arrives, its text is trimmed of spaces at both ends, and the messages before it (`earlier_messages`) go to both the classifier and the agent.
5. **The free gate.** `check_free_gate(text, RateLimiter(st.session_state))` runs before the spinner and before any Grok call. A new `RateLimiter` is built on every run; the counters it reads and replaces live in `st.session_state[RATE_LIMIT_KEY]`. It checks the session cap, then the cooldown, then `prefilter()` (length, then `ATTACK_PATTERNS`). On a block, `log_block()` writes one line to `logs/security.log`, `blocked_answer()` builds the refusal, both messages are marked `blocked`, the fixed refusal is shown with `render_reply()` as an `st.warning`, and steps 6–9 are skipped: no model is created or called. See [SECURITY.md](SECURITY.md) for the rules.
6. **The classifier.** Under the spinner, `ask_grok()` first calls `check_scope(get_classifier_model(), text, trim_history(earlier_messages))`. It asks for a structured `ScopeVerdict` with `with_structured_output(ScopeVerdict, include_raw=True)` (LangChain sends it as a forced tool call). The request is exactly `[SystemMessage(CLASSIFIER_PROMPT), HumanMessage(data)]`, built by `build_classifier_messages()`. The data is the history inside `<conversation>` (one `<user>`/`<assistant>` tag per turn) and the latest message inside `<latest_message>`, all passed through `escape_for_prompt()` first. Only a well-formed verdict of exactly `"YES"` (checked by `read_verdict()`) lets the question on to step 7. A NO, or an answer that can't be read, returns a `Block` (layer `classifier`) and writes one log line. `ask_grok()` then returns `blocked_answer(block)`, which is drawn and marked like a free-gate block, and the agent never runs. See [SECURITY.md](SECURITY.md#the-classifier-what-exists).
7. `run_agent(model, text, units, chat_history)` runs the loop:
   1. It binds `WEATHER_TOOLS` (`get_current_weather` and `get_weather_forecast`) with `bind_tools`. `trim_history()` keeps the last `MAX_HISTORY_EXCHANGES` (2) complete exchanges (a user message followed directly by the assistant's reply), oldest first, as `{"role", "content"}` only: cards, tool data, any other role and any `blocked` message are dropped, and so is a message without its partner. `build_messages()` then sends `[SystemMessage(SYSTEM_PROMPT), HumanMessage, AIMessage, HumanMessage, AIMessage, HumanMessage(text)]`, with as many history pairs as were kept.
   2. It asks the model for its next step. A reply with no tool calls ends the loop, and that reply is returned (or `EMPTY_REPLY_MESSAGE` if it's blank).
   3. Otherwise each tool call runs through `run_tool_call()`, which always puts the app's `units` into the arguments. A call whose `call_signature()` (tool name plus exact arguments) already ran gets a `repeated_call` error instead, and `log_block()` writes a `loop_limit` / `repeated_tool_call` line. Every call gets a `ToolMessage` answer.
   4. After `MAX_TOOL_ROUNDS` (3) rounds the model gets one more turn. If it asks for tools again, those calls are not run, a `loop_limit` / `tool_round_limit` line is logged, and the reply is `TOOL_LIMIT_MESSAGE`.
8. Both tools share `look_up_weather()`: `is_valid_city()` first (no network call if it fails), then the cache (below), then `geocode()` (top match) and a request by latitude and longitude. All requests go through `fetch_json()`. Each tool returns a plain dict: `kind: "current_weather"`, `kind: "forecast"`, or `kind: "error"` with `invalid_city`, `city_not_found`, `service_unavailable` or `forecast_incomplete`. A `service_unavailable` message depends on the `WeatherServiceError`'s `problem` (`SERVICE_ERROR_MESSAGES`: timeout, rate limited, key rejected or unavailable), and every OpenWeather failure is written to the security log with `log_error()` (source `openweather_current` or `openweather_forecast`).
   - `get_current_weather` → `lookup_current_weather()` → `parse_current_weather()`.
   - `get_weather_forecast` → `lookup_weather_forecast()` → `parse_forecast()` → `summarize_forecast(data, now)`, which turns the 40 three-hour entries into exactly `FORECAST_DAYS` (5) days:
     1. `group_by_local_date()` shifts each entry's UTC `dt` by the response's `city.timezone` offset and groups by local date.
     2. The first five local dates on or after the city's local today (from `now`, which is `utc_now()` unless a test passes one) are kept. Earlier and later dates are dropped.
     3. Fewer than five dates raises `IncompleteForecastError`, which the lookup turns into a `forecast_incomplete` error. Days are never invented.
     4. `summarize_day()` gives each day a `label` ("Today", "Tomorrow" or the weekday), its ISO `date`, `high` (largest `temp_max`), `low` (smallest `temp_min`), `condition` (most common; a tie goes to the first in the day), `icon` (the icon of the first entry with that condition, as its daytime version, so `10n` becomes `10d`; None if malformed), `chance_of_rain` (highest `pop` as a whole percent), `humidity` (the average, as a whole percent), `wind_speed` (the highest of the day) and `partial` (fewer than `ENTRIES_PER_FULL_DAY`, 8, entries for that local date).
   - **Cache.** `WEATHER_CACHE` is a `TimedCache` keyed by `cache_key(url, city, units)`: the tool's URL, the city as sent to geocoding and compared without case, and the units. It holds the resolved location plus OpenWeather's raw JSON, and parsing runs again on every hit, so a cached forecast still works out "Today" from the current time. Entries are fresh while under `CACHE_TTL_SECONDS` (600) old and expire at exactly 600. Only a response that parsed successfully is stored; errors (outage, malformed response, `city_not_found`, `forecast_incomplete`) never are. Past `MAX_CACHE_ENTRIES` (128), expired entries are dropped first, then the oldest. The clock is injectable (`time.monotonic` by default).
   - Each result carries its unit labels from `UNIT_LABELS`: `temperature_unit` (both tools) and `wind_speed_unit` (current weather), so the reply and the card agree.
9. **The output scan.** Still under the spinner, `ask_grok()` passes the finished reply to `scan_output(reply, text)`. A reply holding a loaded key, a key-like string, `CANARY` or a code fence becomes `blocked_answer(block)`: the standard refusal as a warning, no cards, both messages marked `blocked`, and one `output_scan` log line. See [SECURITY.md](SECURITY.md#the-output-scan-what-exists).
10. The spinner "Checking the weather…" runs during steps 6, 7 and 9. When the reply passes the scan, it appears (`render_reply()`, as Markdown), followed by one card per successful lookup (`weather_cards()` keeps the `CARD_KINDS`). `render_card()` draws each from the raw result, never from the model's text: `render_current_weather()` for metric tiles, or `render_forecast()` for the forecast card: a header with the location, a row of five equal-height day tiles (`st.columns(5, border=True)`, one `render_forecast_day()` each: a short name from `tile_name()` ("Today", "Sat", "Wed"), date, icon, condition, high/low without the unit (the header caption names it), chance of rain and wind), then a 5-row static `st.table` (Day, High / Low, Condition, Chance of rain, Humidity, Wind) built by `forecast_rows()`, with "(partial)" after a partial day. If either xAI call (classifier or agent) raises, `ask_grok()` returns `friendly_error(exc)` (a fixed message chosen by the exception's type), nothing after it runs, and `log_error("xai", exc)` writes the redacted details to the security log as a `layer=error` event. See [SECURITY.md](SECURITY.md#safe-errors-what-exists).

## Gotchas

- `agent.py` and `app.py` take the model through the `ToolCallingModel` protocol, meaning any object with `bind_tools(tools)` returning something with `invoke(messages)`. Tests rely on this to pass in fakes.
- `create_model()` writes the literal `"grok-4.7"` instead of using `MODEL_NAME`. The two must stay equal. `test_model_is_chatxai_grok_4_7_with_reply_cap_and_timeout` checks this. `create_classifier_model()` in `security.py` writes the same literal, checked by `test_classifier_model_is_chatxai_grok_4_7_at_temperature_0`.
- The classifier takes its model through the `ClassifierModel` protocol: any object with `with_structured_output(schema, include_raw=...)` returning something with `invoke(messages)`. With `include_raw=True`, LangChain returns `{"raw", "parsed", "parsing_error"}` and puts a parse failure in `parsing_error` instead of raising, which is what `read_verdict()` reads.
- **A classifier answer cut off by `CLASSIFIER_MAX_TOKENS` (200) can't be read, so it is refused.** If live testing shows ordinary weather questions refused with `reason=malformed_verdict` in the log, raise the cap first.
- **Every question costs two Grok calls**: the classifier, then the agent (up to four calls in its loop). A classifier NO costs one call and stops there.
- Both tools use the same input schema, `CityInput`. `units` is a field of it marked `InjectedToolArg`, so it is left out of the schema the model sees. The loop fills it in from the sidebar toggle, overwriting anything the model sent.
- OpenWeather's state code only works for US places, and a bare 2-letter code may be read as a country. The `city` field description asks the model for `"Springfield, IL, US"` style. `geocoding_query()` removes the spaces around commas.
- **Fixed offset:** the forecast uses one UTC offset (`city.timezone`) for the whole response. If daylight saving time starts or ends during the five days, entries after the change are an hour off, which can move an entry near midnight to the next or previous day.
- "Today" is the city's date, not the computer's. Late in the city's evening the forecast may have no entries left for today, so the five days start with "Tomorrow" and may all be full.
- The forecast table is a static `st.table`, not an `st.dataframe`. A dataframe is an interactive canvas grid that catches the mouse wheel, so a chat with several of them stuttered while scrolling. `st.table` renders Markdown in its cells, so the only OpenWeather text in it, the condition, must pass `plain_condition()` (see [SECURITY.md](SECURITY.md)).
- Day tiles are about 90 px wide inside a chat message, so their text is kept short: weekday abbreviations and temperatures without the unit. A single long word can't wrap and would be clipped ("Wednesday" was).
- The location on the card comes from geocoding, not the weather response. The weather response often names a district instead (for example "Palais-Royal" for Paris).
- `load_env()` reads `ENV_PATH` when it is called, not at import time, so tests can point it at a temporary `.env`. See [TESTING.md](TESTING.md).
- **One log.** The security log (`SECURITY_LOGGER_NAME`) is the app's only logger. It writes only to `logs/security.log` and doesn't propagate, so neither blocked user text nor error details reach the terminal. Blocks and `layer=error` failures share the file; an error event's indented stack trace follows its first line. `security_logger()` reopens the file if `LOG_PATH` changes, which is how tests point it at a temporary file.
- **An OpenWeather error reaches the user through Grok.** The tool result carries a friendly message, and the model words the reply. The exact wording varies, but it never contains the URL, the key or a stack trace, because the tool result doesn't either.
- **A blocked reply hides its cards too.** If the output scan blocks a reply, the weather cards from that question aren't shown either, even though they come from OpenWeather data, not the model.
- **Long runs of a–f are redacted.** Any run of 32 or more hex characters looks like an OpenWeather key, so a snippet such as 301 `a`s is logged as `[REDACTED]`. This only affects the log, and it errs on the safe side.
- **A refresh resets the limits.** A full page refresh starts a new Streamlit session, and with it new counters (accepted in the PRD). Clearing or re-rendering the chat doesn't.
- **The cache is shared and in memory.** `WEATHER_CACHE` is module-level, so it lasts across Streamlit reruns and is shared by every browser tab, and a server restart empties it. Tests get a fresh one from the autouse `fresh_weather_cache` fixture.
- **The toggle only affects new lookups.** Each card keeps the `units` it was looked up in, so after switching to °C, earlier cards still show °F.
- **History is text the user saw.** Fixed messages such as `UNAVAILABLE_MESSAGE` and `TOOL_LIMIT_MESSAGE` are kept in history like any other reply. Old answers are sent as `AIMessage`s, never in the system prompt.
- **Older forecast cards.** A forecast card saved in an open session before humidity, wind and the day icon were added has none of them. After a code reload it still draws: `humidity_text()` and `wind_text()` show "–" and the tile skips the icon.
